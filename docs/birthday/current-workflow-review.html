3 · Observed bottlenecks & recommendations (separate from the current flow)

Addressed in this round — done

  • Wrong order-reference identity — was EMP{internal id} (EMP530); now EMP{employeeNumber} (EMP396) in detection and manual creation. Existing dev rows corrected by an idempotent, uniqueness-safe backfill (scripts/backfill_order_references.py).
  • Unnecessary supplier selection — the sole ACTIVE supplier is auto-resolved at creation and pre-selected in the panel; still editable; not hardcoded.
  • Unnecessary product-type selection — the generic Product dropdown is gone; Product: Cake is a fixed field. Cake variant stays optional and only shows when the supplier has catalogue items.
  • Unnecessary delivery-date entry — defaults to the birthday occurrence at creation; editable for weekend / holiday / supplier / employee-availability; no extra approval for using the default.
  • REQUIRES_ATTENTION dead end — Submit for Approval now works from REQUIRES_ATTENTION and ON_HOLD; the Fulfilment Assignment panel supplies the supplier/date controls that were missing.
  • Team Member ID display — Option A: Team Member Name (396) on one line; when absent, “(no Team Member ID)”. The BambooHR internal id is no longer shown in the UI.

Still open — for the next round of business-rule decisions — review

  • Address verification is the one remaining manual gate per order (intentional — no automated Team Member contact). Decision: re-verify every year, or carry a VERIFIED + unchanged BambooHR address forward to the next occurrence?
  • Auto-promotion at scan time is effectively dead (address is always NOT_CHECKED then). Either remove the step, or fire the readiness evaluation when the address becomes VERIFIED so the order jumps straight to READY_FOR_APPROVAL with no manual Submit.
  • “Save assignment” click for legacy orders. New orders carry the defaults; pre-fix orders still need one save. A one-off backfill of delivery_date = birthday_date (+ sole supplier) for open orders removes it.
  • Office-location → supplier mapping is brittle for real BambooHR office strings. Sole-active + is_default cover the current single-supplier reality; a region / service-area model is needed before a second supplier.
  • Approval for the fully-defaulted happy path. Every order needs an explicit human approve even when supplier, date, product, quantity and a VERIFIED address are all system-known. Decide whether a “standard order” (all defaults, address verified, normal lead time) may auto-approve, with approval reserved for exceptions (manual override, short lead time, changed address, reassigned supplier).
  • Scan-run history — GET /api/birthday/internal/scan-runs/{id} returns 501; outcomes exist only in the synchronous response.
  • Supplier communications not exposed in BirthdayOrderRead; the order-detail timeline shows OrderEvents only.
  • Two supplier roles (SUPPLIER_USER, SUPPLIER_ADMIN) currently get identical portal permissions.
  • BambooHR pulled live every request (Upcoming Birthdays + detection). A local read model / nightly sync would speed the UI and decouple detection from BambooHR availability.
  • Module /summary endpoint is unauthenticated (platform-wide convention; three integer counts only).
